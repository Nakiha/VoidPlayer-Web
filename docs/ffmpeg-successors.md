# Strict FFmpeg playback successors

Session playback prefers `framesFollowing(displayedPtsUs)`; sources without it use inclusive `framesFrom`. FFmpeg previously lacked the strict interface, so starting playback after presenting frame zero could request that same frame again. It now selects `nextIndex` and uses the existing bounded extraction, progressive index wait and disposal lifecycle. Inclusive reads remain available for their existing callers. Returned buffers stay caller-owned.

Controlled real-client/Worker-message tests prove no extraction before an incremental successor arrives, only index 1 after displayed index 0, waiting at the growing tail, complete EOF, index error and repeated disposal. A restart after releasing the iterator returns indices 2/3 after index 1, without replay or skips. Actual MPEG-2 WASM decoding also exercises strict iteration, restart and EOF; these source-iterator tests do not pretend to drive a full browser pause/resume UI.

The original Chromium local/software H.264 TS cell was checked once with unchanged 2,000 ms, error/stale and positive-draw assertions. It passes the full functional cell and draws 13 frames. [Recorded result](evidence/ffmpeg-successors-cell.json) remains a performance failure (0.133× and presentation stall), using the exact CI playback WASM hashes. This does not fix or explain GL upload/draw long tasks, nor establish full browser or physical hardware acceptance. Historical CI failures are separate environments, not a same-environment browser before/after comparison. No runtime or test deadline/performance threshold changes.
