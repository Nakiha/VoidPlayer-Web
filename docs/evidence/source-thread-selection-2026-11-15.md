# 按片源选择 WASM 线程的本机对照

2026-11-15。Web 使用已推送的 `152c5dd7` 快照，播放和分析使用当前发布锁的 builder `5ccd3566`、FFmpeg `fc5b9f1c`。Apple M5 有 10 个逻辑 CPU，Node 为 24.15.0。WebKit 向页面报告 8 个逻辑 CPU，按当前预留规则，单轨自动预算最多 6 线程。8 线程播放是额外的压力对照。

## 哪些选择值得做

- H.266 整段分析。1080p 及以上且有预算时，4 线程搭配 4 个帧上下文最值得采用。三个大片源都关闭 WPP、使用单 Tile，4 线程配 2 个帧上下文几乎没有收益。同画面 576p 比较中，WPP 和 Tile 的标志都不能单独预测最佳配置。
- H.265。整段 4K WPP 分析保留 2 线程，点查同一 GOP 深处时 4 线程更快。小片源单线程可以降低启动成本。需要结合分辨率、是否需要完整解码、从随机访问点到目标帧要解多少帧，才能决定是否加线程。
- H.264。当前分析使用帧线程。把同一画面从每帧一个切片改成四个，线程选择结论相同。4K 上 Node 和 WebKit 的最优方向不同。
- 播放。在单轨低分辨率、30 fps、有清楚首包和配置证据的三个样片上，2 个解码线程足以维持实时。对于大画面，离线解码吞吐可用于衡量余量，实际播放决策还应看上屏和掉帧。

## 测量口径

所有表均取单次独立测量的中位数。两种编码特性对照使用相同的原始画面。H.266 使用 960×576、64 帧、10-bit 低延迟编码，分别只开 WPP、只开 2×2 Tile、两者都关；H.265 使用 960×540 和 1920×1080 的 WPP 开关对照；H.264 使用 960×540 的 1/4 切片对照。片源哈希、参数集和首包计数见配套数据。只测受控 MP4、单机单任务，未覆盖多轨竞争、手机、其他浏览器、硬件解码、画质指标或服务端数据库入库。

Node 每次新起进程，按片源轮换线程顺序，共三轮。播放使用实际 MP4 引擎、内存文件和多线程 WASM。首帧预热后连续取出余下全部帧，逐帧核对 PTS。每个线程配置另做一轮逐帧像素和 4 个 seek 的哈希校验，哈希工作置于计时之外。分析使用正式 runner 的 blocks 产品，输入已在内存中。吞吐计时含产品生成，不含创建 core 和事后比对哈希。附带的冷耗时包含 core 初始化，仍不含进程启动、文件读取、HTTP 或数据库。

WebKit 播放通过真实媒体库、会话 benchmark 和 WebGPU 画布完成，强制 FFmpeg WASM，并从轨道信息核实实际解码线程数。浏览器本地分析使用正式构建的 local Worker、真实 File、空缓存回执和逐帧交付。耗时从提交任务到收到最终回执，含 Worker 启动、core 初始化和结果传递，未计入事后哈希或面板绘制。每次新建 Worker，浏览器可以复用已加载资源。浏览器单线程对照走产品的单线程产物，Node 分析各档位使用同一多线程产物。所有同片源、同目标的播放或分析哈希在不同线程下均一致，可对照的 Node/WebKit 分析哈希也一致。

## 对实现的影响

WPP 和 Tile 可从容器已有的初始 SPS/PPS 取得，首包 VCL 数只代表该包。当前播放先打开解码器，随后发送首包时才记录计数。若建池前需要这个数，应复用已读的首包；布局未知、参数集歧义或中途切换时沿用现有预算，不必为打开左面板启动深度分析。服务端分析 Worker 可从自己打开的输入获取信息，浏览器本地分析可以利用已打开轨道提供的配置。

播放侧的线程预约还会在可用预算恢复时自动增长。实验里只改初始值，2 线程会涨回 4 或 6；最终的降档对照同时限制了当次预约的增长，并核对实际线程数。正式实现需要在初始分配和恢复预算时遵守同一片源上限，同时保留多轨总预算、手动设置和无跨源隔离时的单线程路径。
