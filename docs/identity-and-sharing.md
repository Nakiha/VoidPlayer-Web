# 用户、访客与工作区分享

## 身份创建时机

用户身份只在 `POST /api/identity` 明确填写用户名时创建。`GET /api/health`、媒体浏览、工作区读取、标注读取与管理页面读取均不创建用户，也不补写身份 cookie。

首次打开播放器或管理页，cookie 缺失、无效或对应用户不存在时，展示选择界面：选择已有用户、填写用户名、以访客继续。界面说明可在设置 → 用户中修改。访客是 `guest-<UUID>` cookie，显示名统一为“访客”，不插入 users 表；刷新与服务重启后沿用 cookie。访客保存的数据仍以其访客 ID 记录归属。清除 cookie 后无法自动找回访客身份。

身份接口接受 `{name:string}`、`{id:string}` 或 `{guest:true}`。写入工作区、标注前必须显式选择身份；HTTP agent 应先调用该接口并保存 cookie。健康检查不代表登录。名字沿用可信内网的自主声明模型，不是身份证明；同名表示切换到已有身份，不迁移另一个身份的历史数据。

数据库 v3 为旧用户增加 kind：旧版自动生成格式 `用户-xxxxxxxx` 迁移为访客，保留 ID 和所有历史引用，不删除数据、不按前缀持续推断新名字。已有用户列表仅返回 named；旧访客仍可用原 cookie 打开自己的工作区，明确填写名字可保留其 ID 升级。这个一次性迁移无法区分过去手工填写的完全同格式名字，可通过重新设置用户名恢复。

## 分享可读写工作区

播放器和工作区页的「分享」执行同一个动作：保存当前工作区并复制 `/?workspace=ID` 链接。接收者打开链接可还原片源、播放位置、对比条件和布局，随后可编辑，并用现有「保存工作区」写回同一工作区。再次点击分享也保存当前内容并复制同一个地址。

分享不再要求创建评审、发布进展、选择版本或生成只读副本。复制权限不可用时仅显示可选中的链接。工作区名称在设置 → 工作区中修改，分享入口不另设命名步骤。

共享工作区与普通保存的工作区统一存入 workspaces.sqlite 的 workspaces 表。更新仍使用 If-Match 避免双窗口静默覆盖，冲突沿用工作区的重新打开操作。可信内网用户可以读取和保存同一工作区，用户身份记录归属，不作为认证权限。

标注读写关联到工作区的当前标注数据，按前台每 3 秒增量同步；草稿保留在 IndexedDB。打开链接不重新导入文档中的旧标注副本，因此别人修改或删除标注后，链接按当前数据加载，不会复活删除记录。分享期间的新增、修改或删除也保留。回复和解决状态仍走 session.updateMark。

链接是可变工作区的入口，不承诺永久复现第一次分享时的效果。文件、标注或工作区内容改变后，重新打开反映当前数据；源文件被删除或不再可访问时，显示缺失片源并允许重新关联。各页面正在查看的播放位置与布局仍独立，打开或重新载入链接时才还原已保存内容。

分享只支持服务端可访问的媒体库片源，本地文件需先放入媒体库，不隐式上传。媒体引用固定库版本用于身份校验与缓存；这不保证源文件的永久可用性。同服务不同域名访问时，媒体引用映射到接收者域名，外部库保留原地址。色彩与解码契约沿用工作区格式。

## 旧链接兼容

旧 `?share=ID` 和 `?review=ID` 首次打开时接入同一可读写工作区，之后使用 `?workspace=ID`，原数据不删除。旧评审沿用现有标注数据，旧快照的初始标注仅按幂等操作导入一次。迁移后的工作区若被删除，不因再打开旧链接而重新创建。

新分享不再写入不可变快照或评审版本表。旧表保留兼容读取，历史版本、固定副本和进展发布不再作为产品入口。工作区、标注正文和回复仍属于用户数据，不能通过缓存清理删除。
