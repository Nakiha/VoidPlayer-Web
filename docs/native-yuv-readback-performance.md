# WebCodecs 原始平面读回拆测

2026-09-11，Windows RTX 5080，Chrome 153.0.8010.36 / Edge 152.0.4191.66。使用用户 4K HEVC 原片。路径为 WebCodecs 原生 NV12 → copyTo 原始 YUV → 共同 WebGPU shader；没有浏览器 YUV→RGB 中间转换。

`node scripts/bench-native-readback.mjs` 比较复用 ArrayBuffer、复用 SharedArrayBuffer，以及将 VideoFrame 转移到 Worker 后的两种缓冲。每种路径每轮 30 帧，共两轮；第二轮倒转顺序，降低预热顺序影响。所有路径的首帧 SHA256 相同。共享缓冲只在 copyTo 完成后交给 GPU 上传，下一次写入发生在本帧 GPU 工作完成之后。

| 路径 | Chrome copyTo p50（两轮） | Edge copyTo p50（两轮） |
| --- | --- | --- |
| 主线程 ArrayBuffer | 18.86 / 18.03 ms | 10.67 / 10.23 ms |
| 主线程 SharedArrayBuffer | 18.21 / 18.02 ms | 10.41 / 10.34 ms |
| Worker ArrayBuffer | 18.01 / 18.16 ms | 10.43 / 10.47 ms |
| Worker SharedArrayBuffer | 17.89 / 18.25 ms | 10.17 / 10.29 ms |

这是串行读回实验，不是完整播放 fps：循环计时不包含异步迭代器取得下一解码帧的时间，每帧等待 GPU 完成；包含读回、上传和全分辨率 shader 的串行耗时约 Chrome 25 ms、Edge 17 ms。不能将其直接当作流水化播放上限。Worker 通信另有小额开销；本次共享缓冲和 Worker 没有显著降低原生读回成本。

结论：正确颜色不必在原理上绑定 WASM。可采用硬解 + 可读原始平面 + 共同 GPU 呈现，但本机 4K 资源的读回成本很高。后续流水线结果见下文；其他分辨率、GPU 和资源布局尚未验证。仍需处理不透明高位深格式、原生色彩/色度位置标签缺失与错误，不能仅因 copyTo 成功就认证颜色语义。

报告：`artifacts/color/native-readback.json`。此轮只增加诊断，没有改变两种用户模式的默认后端。

## 有界流水线与真实 WASM 对照

同日运行 `node scripts/bench-yuv-pipeline.mjs`，使用相同原片、浏览器与显卡。WASM 为 Actions 34499068492 的真实多线程 core（上游修订 1ba3ef85088797ed37133e19580bbd05805bde9f，ABI 2），不是模拟解码器。每个浏览器比较 WASM、主线程 copyTo、Worker copyTo 三条路径，各测队列深度 1、2、4、8，两轮共 48 组，第二轮反转顺序并重新启动浏览器。

计时包含完整片段的解码、原始平面读回、上传及 GPU 完成等待；打开文件和首次预热不计。4K YUV 上传后统一由 planes shader 呈现到 960×540 画布。生产者与按顺序消费的呈现端独立推进，Worker 路径每个槽位一个 Worker、复用可转移 ArrayBuffer；CPU 帧槽位与待完成 GPU fence 数分别受深度限制。这里测的是无播放时钟限速的单轨处理吞吐，不是实际 UI 播放帧率，也不能与前面的全分辨率串行呈现耗时直接比较。

| 浏览器 / 路径 | 深度 1 fps | 深度 2 fps | 深度 4 fps | 深度 8 fps |
| --- | --- | --- | --- | --- |
| Chrome / WASM | 74.40–75.09 | 74.90–75.52 | 75.50–76.12 | 74.22–74.82 |
| Chrome / 主线程读回 | 44.74–46.05 | 46.24–46.27 | 46.59–46.74 | 44.31–44.71 |
| Chrome / Worker 读回 | 43.81–44.29 | 46.17–46.68 | 47.22–47.41 | 46.77–47.77 |
| Edge / WASM | 74.10–74.69 | 74.21–76.12 | 76.39–77.10 | 75.23–75.86 |
| Edge / 主线程读回 | 70.21–71.33 | 70.69–71.60 | 73.24–73.90 | 69.62–69.67 |
| Edge / Worker 读回 | 68.08–69.18 | 74.60–74.85 | 75.85–76.26 | 73.67–75.25 |

CPU 指标使用 CDP 浏览器进程树累计 CPU 时间差，包含 renderer、Worker、GPU/utility 等被枚举进程，除以完成帧数。它是各核时间之和，不是主线程占用率或任务管理器整机百分比；进程退出可能导致遗漏，测量窗口也包含少量 CDP 往返。各组都完成 180 帧。

| 深度 4 对照 | WASM CPU ms/帧 | Worker CPU ms/帧 | 两轮均值 CPU 降幅 | Worker 吞吐相对 WASM |
| --- | --- | --- | --- | --- |
| Chrome | 52.64–52.93 | 22.75–22.90 | 56.8% | 62.4% |
| Edge | 51.39–52.44 | 14.44–14.91 | 71.7% | 99.1% |

Worker 确实同时持有了 1、2、4、8 个待读回帧，因此不是只改队列参数而仍串行等待。但 Chrome 单次 copyTo 中位数从深度 1 的约 21 ms，增加至深度 2 的 41 ms、深度 4 的 81 ms、深度 8 的 163 ms；Edge 分别约 13、25、50、88–91 ms。copyTo 的同步调用时间与整个 Promise 完成时间接近。现象支持底层读回存在共享串行瓶颈或资源争用的判断，无法仅据此定位到驱动锁或浏览器具体函数。Worker 可以移走主线程阻塞，不能让这些读回自动获得线性并行加速。

8-bit 4K 4:2:0 紧密平面每份约 11.87 MiB，深度 2/4/8 的名义 CPU YUV 缓冲预算约 23.7/47.5/94.9 MiB（不含解码器内部队列、行对齐、GPU 上传缓冲及纹理）。Worker 深度 2→4→8 的浏览器进程工作集峰值，Chrome 为 1081–1159→1154–1202→1246–1339 MiB，Edge 为 903–947→977–1017→1092–1093 MiB。数据每 200 ms 采样；工作集求和会重复计入共享页，不包含独立显存，也受此前测试的分配器缓存影响，不能据此推断精确内存节省。未测得增加到八帧带来的吞吐收益。

所有 48 组均通过完整 PTS 顺序相等、每帧 16×16×3 原始 YUV 抽样指纹相等、CPU/GPU 队列有界断言。这证明本实验没有靠跳帧提高吞吐，抽样也没有出现平面内容差异；不等同于全部像素逐字节比较，或最终 RGB 色彩契约验收。原生读回实验尚未补全色度位置等元数据，因此不能直接用作“正确颜色”模式的生产后端。

结果支持继续开发有界的硬解原始平面路径：Edge 可在本片单轨保持接近 WASM 的吞吐，同时大幅降低 CPU 时间；Chrome 的 CPU 时间同样降低，但达不到本片约 60 fps 的实时需求，仍需 WASM。建议初始只保留 2–4 个槽位，按实际能力与运行时吞吐选择，不能按浏览器名字硬编码。正式启用前还需验证双轨、较长播放、seek/取消清理、色彩元数据与高位深边界。本轮只新增基准脚本和记录，未更改生产默认后端。
