# 时间线兼容性：恢复显示顺序，不按文件打补丁

## 本轮落地

HEVC MP4 如果没有 composition offset，却在码流中存在图片重排，原先会按错误的包时间展示画面；软件包路径则在重复的 best-effort 时间处失败。

现在使用独立的 `hevc-timeline.ts` 读取有界的 SPS、PPS 和首 slice 头，建立完整的图片显示顺序。只有结构和时钟都能证明一致时才应用恢复：单层渐进 Main/Main10、单配置、闭合 IDR GOP、每个 GOP 的 POC 唯一且连续、原包时钟等距且唯一。正常 composition offset、零重排上限的低延迟流、VFR 和不完整的图片序列不会被猜成固定帧率。判断不使用文件名、大小、哈希或某个固定 GOP 长度。

恢复将原有等距时钟的时间槽分配给正确的图片，不重编码，不用输出回退后临时加帧距的方法。MP4 原生和软件路径共用 `PacketTimeline` 的播放、逐帧和定位逻辑；原始 PTS 保留在包描述和错误上下文，来源通过 `timelineSource` 和 `indexWarning` 进入诊断。

WebCodecs 请求硬件优先。此偏好表示浏览器接受了配置，不是实际硬件使用率的证明。负的源时间只在送入 WebCodecs 时平移；接收时在帧描述中恢复逻辑时间，不重建 GPU 像素资源。这样首帧、预滚图片和整个显示序列共用一个时间基准。

验收新增了完整 600 帧的像素参考、GPU 上屏与回读、关键帧前后定位、倒退定位、逐帧、尾帧、本地/Range 和关闭重开。原始坏片保留，另有独立生成的语法测试覆盖低延迟 B 帧、POC 回绕、参数集标志和多 GOP。测试中 SHA 只用于固定参考素材，生产路径不读取 SHA。

浏览器的原生路径使用独立固定的 FFmpeg 显示顺序生成参考，再要求生产路径的 YUV 平面取样逐值一致。生产路径的 POC 解析结果不参与生成参考。这样不会将不同平台的有限/全范围或 RGB 矩阵转换混入帧序判定。软件 RGBA 输出保留原有像素参考；跨后端 RGB 差异仍记入报告，GPU 上屏另与同一浏览器的画布输出核对。

复现：

```sh
node --test test/hevc-timeline.test.ts
npm run test:hevc-timeline:browser
```

本机验收：291 项 Node 测试通过，生产构建通过；WebKit/Chromium 共 8 次完整的 600 帧检查通过。实际播放器基准中，修复片与正常 4K HEVC 共 6 次运行通过，修复片播放速度约为 1.0 倍。60 Hz 调度仍有独立的丢帧波动，这些结果不表示已经解决所有播放调度问题。

## 新增 FATE 调查

`scripts/fate-timestamp-samples.json` 固定了 6 个官方文件的 URL、大小和 SHA-256。它们包含截取的 TS、节目表变化、场编码以及缺少完整起始画面的片段。官方样片不等于每个都专门测试坏时间戳：本轮这 6 个文件经原生 ffprobe 检查，没有出现解码帧时间回退。

因此额外提供 `make-timestamp-fixtures.mjs`，对固定的官方 TS 注入可重复的时钟变化，不修改压缩图片：33 位时钟回绕、向前跳 30 秒、时钟重置，以及重复整个片段。派生文件明确标为派生测试，不能冒充官方 FATE 原片。

```sh
node scripts/sync-fate-samples.mjs
node scripts/make-timestamp-fixtures.mjs
node scripts/check-timestamp-corpus.mjs
```

调查使用原生 FFmpeg 的顺序解码和 RGB 区域均值作参考，覆盖 Node/WASM、WebKit/Chromium、本地/HTTP、连续输出、定位和重开。报告位于 `.run/playback-reports/timestamp-corpus.json`。普通运行遇到失败会返回失败；CI 的探索步骤使用 `--report-only` 保存所有失败，**不把这些失败变成通过，也不替代 HEVC 修复的硬门禁**。

本轮实际暴露的问题：

| 情况 | 当前表现 | 所需能力 |
| --- | --- | --- |
| PTS 前后变化，但 DTS 连续 | 可能只是正常 B 帧重排 | 不能把所有 PTS 回退当坏片 |
| 33 位正常回绕 | 原生 FFmpeg 能输出完整序列；当前 WASM 容器索引/抽帧路径未能起播 | 展开时钟后建立一致的起点和寻址 |
| 向前跳 30 秒 | 可以逐帧遍历，但时间线保留了长间隔 | 保留真实间隔，提供明确的跨间隔导航；不能擅自压缩时间 |
| 时钟重置 | 原生参考保留 74 帧；浏览器路径只输出 53 帧，软件路径抽帧失败 | 索引必须表达不同时钟段，不能只按 PTS 找帧 |
| 重复片段 | 原生参考有 148 帧；全局 PTS 排序造成帧位置混淆，部分浏览器路径等待不结束 | 图片身份应包含片段和顺序，避免同 PTS 合并或错误定位 |
| 截断/场编码/缺少可解码开头 | 可能出现包数与实际图片数不一致，或始终抽不到首个索引帧 | 从解码输出建立图片索引，首帧以实际可解码结果为准 |
| 未标明色彩的 H.264 | 浏览器与软件参考有色彩转换差异，帧数正确仍可能失败 | 独立核对未声明色彩时的后端策略，不能用放宽时间检查掩盖 |

`pmtchange.ts` 在本次原生参考中也没有可解码视频帧，不能把其拒绝直接解释为播放器丢帧。HTTP/WASM 的跨源隔离限制、超时、参考为空和实际像素不匹配需分别看报告，不合并为一个“解码错误”。

## 下一阶段的结构整改

WASM 容器 core 的 `vp_index_build` 当前主要收集包 PTS，再全局排序；`vp_extract` 要求解码输出的 best-effort 时间精确命中该 PTS。这个模型无法可靠表达重复时钟段，以及一个包并不对应一张显示图片的输入。单纯删掉 TS 层的单调断言不能修复这个模型。

按以下顺序推进，修改 core 时在 `VoidPlayer-FFmpeg-Build` 完成并锁定发布修订：

1. **图片身份与寻址。** 将包位置/解码顺序和输出图片身份分开，图片索引表达 `ordinal + clockEpoch + originalPTS + presentationPTS + seekAnchor + configurationEpoch`。顺序播放消费实际解码输出；定位使用所属时钟段的字节/GOP 锚点，不能跨段用相同 PTS 误命中。
2. **时钟段。** 33 位模回绕在解封装边界展开。真正重置依据 DTS、PCR、discontinuity 和配置证据建立新段；不能凭一个回退的 PTS 判定。正常 VFR 和正向空档保留原有时间关系。需要拼接评审时间时，在整段映射中明确记录偏移，而不是边播放边改表。
3. **索引与首帧。** 不把包数承诺为显示帧数。对无法通过包表证明可定位性的输入，用实际输出建立索引并报告构建状态；不完整起始 GOP 的跳过必须在首帧和时长元数据中一致体现。
4. **统一验收。** 使用独立图片参考检查完整序列、段边界前后定位、重复定位、关闭重开、元数据与标注时间；将找到的输入结构转为一般规则测试，再保留真实 FATE 样片作为集成验证。失败保持可见，不能只检查“没异常”。

HEVC 本轮的闭合 GOP 恢复已经是上述“分开图片顺序和包时间”的一部分；它不是对所有损坏 PTS 的完整解决方案，也不能宣称 TS 的时钟段整改已经完成。

参考：[WebCodecs 输出与时间戳约定](https://www.w3.org/TR/webcodecs/#videodecoder-interface)、[FFmpeg HEVC 图片头解析](https://ffmpeg.org/doxygen/7.1/hevc_2parser_8c_source.html)、[官方 MPEG-TS 样片目录](https://fate-suite.ffmpeg.org/mpegts/)。
